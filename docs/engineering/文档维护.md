# 文档维护

## 目标

`fdst/docs` 同时服务设计读者和工程维护者，但两类内容分开组织：

- `foundations/`、`semantics/` 面向设计、产品和使用 Token 的开发者，优先说明原则、场景和视觉结果。
- `getting-started/`、`concepts/` 面向接入与架构读者。
- `engineering/` 面向 Token 维护者，保存 YAML、构建、校验、版本和发布细节。
- `reference/Token目录.md` 是自动生成的完整索引，不手工编辑。

设计读者通过 `public/` 内部预览站阅读。`docs/` Markdown 是内容源，`docs/site-assets/` 保存站点壳层和可复用 Demo，`public/` 由 `tools/build_docs.py` 确定性生成，不直接编辑。独立的对外预览文稿保存在 `docs/external/`，生成到 `public-external/`；逐页分类和发布边界见 [站点内容分流清单](../站点内容分流清单.md)。两个输出目录目前都不是正式发布站点。

内部文档站顶部按“基础规范、使用指南、Token 目录、内部工程”导航；左侧只列当前分区的页面，首页仍作为总入口。基础规范包含视觉基础、语义和视觉预览；使用指南包含快速接入、概念规则和迁移常见问题。新增页面先确定读者任务和所属分区，再加入 `tools/build_docs.py` 的导航配置；尚无正式内容的组件和场景案例不建立空入口。对外预览继续使用独立的公开内容清单，不继承内部工程导航。

## 数据来源

```text
tokens/fds-global.yml import 图
  -> release/fds-global-tokens.css
  -> release/fds-global-tokens.min.css
  -> release/fds-token-catalog.json
  -> docs/reference/Token目录.md
  -> public/ 可视化文档站
```

CSS 是页面、组件和视觉预览的运行时交付物。catalog JSON 是文档生成、查询和校验的派生数据，不是设计人员必须使用的接入格式。
文档站的排版、圆角、间距、阴影、透明度、层级、动效和语义颜色示例数据由 `tools/build_docs.py` 从 catalog JSON 提取并生成 `public/assets/fds-demo-data.js`；排版、间距、圆角、动效和效果页的当前值域表格也在构建时从 catalog JSON 生成。Markdown 保留使用原则、场景说明和示例文案。色阶页面仅展示 `docs/site-assets/project9-palette.json` 保存的项目9本地评审色板快照，并明确标记为临时预览；公司当前的彩色色板不进入网页预览数据。快照只用于文档站，不参与公司 Token 构建、Catalog、Skill 查询或发布。更新快照时核对项目9的 Primitive、Map 和生成的 Foundation manifest，记录文件 hash 后复制到本仓库，不在构建时读取项目9目录。修改 YAML 后先更新 catalog，再重建文档站。

## JSON 事实与说明文字

排版页的角色表、密度表、数值和 CSS 示例均从 catalog JSON 生成；颜色页的主操作映射、间距页和场景语义页的密度值也从 JSON 生成。命名规则和 YAML 源文件页中的 `color-primary` 示例同样随当前 Catalog 引用生成。圆角、动效与效果页保留设计说明，具体数值显示在 JSON 生成的值域与示例中。视觉工作台的候选色板单独标记来源。构建时会检查所有站内 Markdown 中完整写出的 FDS CSS 变量是否仍存在。迁移与常见问题页保留旧系统的历史数值，并明确标记用途。构建校验只能保证已生成的数据和变量引用与 Catalog 一致；使用建议、能力边界及历史映射仍需人工评审。

## SDS 文档迁移规则

1. 迁移 Token 总览、颜色、排版、间距、圆角、透明度、阴影、层级和动效等详细 Token 内容。
2. 保留 SDS 的 `teaches`、`use_when`、任务型标题、设计原则、使用场景、Do / Don't 和视觉示例习惯。
3. 不复制 SDS 中的旧 Token 名称、数值、算法或真相源描述；所有事实按当前 YAML、CSS 和 catalog 校正。
4. Grid、Layout、Icons、Charts 等混合页面只迁移其中的具体 Token 说明，宏观设计规范继续留在 SDS。
5. SDS 对已迁移的 Token 主题改为链接本仓库，不再保存详细副本或读取 catalog 重新生成一套页面数据。

## 页面维护顺序

1. 先确认页面属于 Token 详细规范，而不是 Components 或其他宏观设计规范。
2. 从 catalog 和 YAML 核对名称、值、层级、引用和当前能力边界。
3. 按“目标 -> 原则 -> 场景 -> Do / Don't -> 视觉示例 -> 工程来源”组织内容。
4. 需要视觉示例时，在正文对应位置加入 `data-demo` 容器，并复用 `docs/site-assets/fds-demos.js` 中的现有 Demo；不得在单篇页面复制一套 CSS 或 Token 值。
5. 运行 `python tools/build_docs.py` 生成 `public/` 和 `public-external/`，再运行文档校验。
6. 在发布记录中注明 Token 版本和文档变更范围。

## 校验

```powershell
python tools/build.py --check
python tools/export_catalog.py --check-docs
python tools/build_docs.py --check
python -m unittest discover -s tests -p "test_*.py"
```

文档不得手工维护完整 Token 清单，不得把 catalog JSON 描述为设计侧的主要接入产物，也不得把尚未发布的本地生成物写成线上已可用。
